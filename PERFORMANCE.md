# Fennec — Performance & Caching Strategy

> Reviewed 2026-07-09. The rule: compute the expensive thing once, cache it,
> and never make a user wait for work that can happen out of band.

## 1. Database indexes

Postgres auto-indexes primary keys and UNIQUE constraints, nothing else. Every
hot filter column now has an index (migration `20260709_perf_indexes.sql`):
`business_projects/quotes/clients` and `project_reviews` by `(user_id, created_at)`,
`review_comments` by `(track_id, created_at)`, `notifications` by
`(user_id, read, created_at)`, `voice_notes` by `recipient_id`/`sender_id`,
plus the feed (`posts`, `comments`, `vibes`, `bookmarks`), `karma_ledger`,
`push_subscriptions`, `suggestions`, and `bot_posted_urls`.

When any table crosses ~100k rows, rebuild its indexes with
`CREATE INDEX CONCURRENTLY` (outside a transaction) so the build doesn't lock writes.

## 2. What is cached, and where

| Data | Layer | TTL | Notes |
|------|-------|-----|-------|
| Trending videos | `cached_content` table (Supabase) | 6h | One shared fetch for all users. Written by service-role. |
| Personalized "your angle" | `cached_content`, key per genre combo | 6h | One Haiku call per genre COMBO, not per user. |
| Industry news | `cached_content` + HTTP `s-maxage=3600` | 2h | CDN-cached at the edge too. |
| Social follower counts | `profiles.*_followers` + `social_synced_at` | 6h | Cooldown in `/api/social-stats`; scrape only past the window. |
| Fennec dB score | `profiles.fennec_db_score` | on change | Computed once in the Dashboard, persisted; readers use the stored value. |

**Rule for new expensive reads:** if it hits an external API (Apify, Claude,
YouTube, Spotify) or scans a whole table, cache the result in `cached_content`
(shared) or on the row (`profiles`), key it by whatever it varies on, and gate
re-computation with a timestamp + TTL. Never call the external API straight
from a component.

## 3. Heavy work stays off the request path

- **Trending / news / notifications** are generated by **cron** (`vercel.json`
  crons → `/api/cache-refresh`, `/api/cron/*`), not in a user request. Users
  read the pre-warmed cache instantly.
- **Social scrape** (Apify, 15-25s) no longer runs on every dashboard mount:
  the 6h cooldown returns stored counts immediately; only a genuine refresh
  past the window pays the cost. The weekly cron keeps everyone fresh.
- **Push fan-out** runs inside the cron / notification routes, not blocking the
  action that triggered it.

### Still worth doing (not yet done)
- Make the *first* social scrape truly background: return the cached/empty
  counts instantly and let the scrape finish out of band (e.g. Vercel
  `waitUntil`, or a queue), instead of holding the 60s function. Today the
  cooldown means only the first sync per 6h window waits.
- Consider caching the admin `/overview` aggregates (full-table scans per
  request); low priority since it's admin-only, low traffic.

## 4. Load testing (before launch)

Run real simulated traffic to find what breaks under load: concurrent signups,
feed reads, tape marks, and dashboard loads (which fan out to profile + business
+ social queries). Watch for slow queries (confirm the new indexes are used via
`EXPLAIN ANALYZE`), Apify/Claude cost spikes, Supabase connection-pool limits,
and Vercel function timeouts. Tools: k6 or Artillery against a staging project,
never production. This is a pre-launch gate, not a nice-to-have.
